# Cordis 与 deepseek-harness 研读总览

> 素材：论文《A Programming Paradigm for Spatiotemporal Composability》（arXiv:2608.25512，北京大学与 DeepSeek-AI，2026，v1 全文 92 页，正文至 83 页）与仓库 deepseek-ai/deepseek-harness（下称 dsh，2026-10-01 勘察）。本总览由七份板块笔记融成，细分笔记在 `研读笔记/素材/` 目录下，页码均指论文印刷页码。文中出现的页码、定理号、规则条数都只当索引用：想核对再翻素材笔记，不核对也完全不碍事。

## 一、一页纸总览

先说结论。这套工作回答的问题是：软件能不能像换零件一样，在运行中途把一个组件拆下来，拆完不留垃圾、不惊动别的组件。今天的通行答案很粗暴：重启进程。为换一个灯泡拉下整栋楼的电闸，代价是进程内状态全丢、要养冗余副本、进行中的任务反复被打断。论文把这件事拆成两个互相独立的考题。一是拆得干净（时间维度）：拆走一个组件时，它对共享环境做过的每件事都能撤销。二是接得稳（空间维度）：组件之间的依赖是声明出来的，环境一变，谁该开机、谁该歇业，系统自动决定。

解法的思路是把编程语言理论里躺了四十年的两个纸面概念搬进运行时。效应（effect）指程序对外部世界的改动，论文要求每个改动当场附带一份撤销说明书，交给运行时串成回执链；反效应（coeffect）指程序要求环境先提供什么，论文要求组件进门先交需求清单，环境每次变化都拿清单对照一遍，自动决定启停。两本账合并成一本总账，就是语境（context），所有组件和环境的交互都从这一个门走。

落地分三层：论文是理论；Cordis 是理论的开源实现（TypeScript 元框架）；dsh 是它在 AI Agent 领域的旗舰应用，DeepSeek 开源的 agent harness（包在模型外面那层骨架，管装配工具、权限、沙箱、会话记录），口号「一切皆插件」，模型适配器、工具注册表、会话日志甚至 agent 循环本身都是可替换的插件。在这之前，同一套核心库已经养出了 Koishi：一个跑了四五年、有几千个社区插件的聊天机器人框架，先例证明这套范式养得起大生态。

为什么值得你懂：论文作者自己点名，这套范式最有价值的验证场是「自进化 agent harness」，也就是 AI 持续生成并替换自己运行环境组件的系统。快速替换考验拆得干净，拓扑频繁变动考验接得稳，两个保证正好一一对应；论文参考文献里就引着 OpenAI 和 Anthropic 的 harness 工程文章。对做 agent 开源项目的人，可以先记两条底线：每个动作登记可撤销的逆操作；依赖不满足就安静休眠，别报错。

证据力度也要说诚实：Koishi 是「存在且有人用」的观察性证据，单一生态、单一语言、没有对照实验，性能开销论文自己承认未量化。dsh 创建七周就有 24 万 star，但项目自曝处于 developer preview、会有破坏性变更。判断思想成熟度，Koishi 比 dsh 更有参考价值。

## 二、通俗词典

按重要程度排，够用为准。

- **效应（effect）**：程序对外部世界留下的改动，写文件、开端口、注册一条命令都算。论文要求每个效应自带撤销办法。
- **反效应（coeffect）**：效应的镜像。效应说「我对世界做了什么」，反效应说「世界得先给我什么」：资源、权限、服务。说白了就是依赖清单。
- **语境（context）**：全系统共用的一本大账，记着当前状态、所有撤销办法、所有依赖登记。论文的纲领是组件和环境的每一次交互都经过它，谁也不许绕开。
- **组件（component）**：一份岗位说明书，含三份文件：我需要什么、我能提供什么、我上岗后干什么（每件事附撤销办法）。
- **纤维（fiber）**：说明书的一次具体上岗。组件是职位描述，fiber 是某年某月入职的那位员工，从入职到离场有固定流程。
- **可逆（revertible）**：改动的附赠品。谁做的改动谁当场交出撤销函数，运行时统一保管，卸载时按后进先出执行。
- **响应式（reactive）**：依赖是活的。环境每变一次，运行时拿每个组件的需求清单对照一遍，从缺到齐就激活，从齐到缺就停用，其余不理会。
- **累加器**：把所有撤销函数按顺序串成的一个总函数。卸载组件时调用它一次，环境整体还原，效果像按一次键全退光的 Ctrl+Z。
- **inject（依赖注入）**：插件在门口声明「我要用 ctx.llm」，框架等它就绪才启动插件。插件自己不找依赖，也不写监控代码。
- **isolate（隔离）**：同名依赖在不同上下文各指向一份私有值。像合租屋里隔出的独立储物柜，多租户、测试环境、沙箱都靠它。
- **intercept（拦截）**：在「读依赖」这个动作外面叠一层规则，外层能约束内层怎么用依赖，双方代码都不用改，改规则不用重启。
- **观察等价**：两个状态算「一样」，指任何合法操作跑下来都看不出区别。退房验收的标准是下一位客人察觉不出，不要求灰尘的排布也复原。
- **交换性与独立性**：两个操作可交换，指谁先谁后结果一样；两个组件独立，指互不弄坏对方的产出。不同储物格上的操作天然独立，同一格内部由格子的提供者负责保证。「认证」具体是个什么动作，见思想三。
- **进展与汇聚**：进展指系统折腾的步数有限、停得下来（前提是依赖不成环、组件总数有限）；汇聚指停下来的位置只由最终配置决定，中间装了又拆、拆了又装不留痕迹。菜的味道只看最终配方。
- **声明式配置**：用一份配置树描述「系统应该长什么样」，加载器负责把现实改成和清单一致，改动按最小动作分发，不推倒重来。
- **热模块替换（HMR）**：改了源码文件，程序不重启，原地换掉受影响的零件。Cordis 的重载是事务性的：先备份，失败整体回滚，永不半新半旧。
- **生命周期**：一个零件从装上到拆下经过的固定阶段。论文里 fiber 有四态：空闲、激活中、在岗、停用中，怎么流转由九条规则管（九条规则在思想四走读）。
- **能力接缝（capability seam）**：dsh 的术语。一个能力由「接口 + 提供者 + 消费者」三件套组成，接口稳定，实现随便换，换一次全局生效。
- **作用域（scope）**：dsh 的隔离层。每个 agent 一个注册作用域，子 agent 看不到父 agent 私有的注册。
- **Agent harness**：包在 AI 模型外面的一层骨架，负责装配工具、管权限和沙箱、记会话。可以理解成「给 AI 用的工具箱加操作系统」，dsh 就是一个 harness。

## 三、核心思想逐个讲透

### 思想一：把「撤销」从个人美德变成制度

**问题是什么：**插件卸载留垃圾是行业常态。常见的写法把「制造影响」和「清理影响」放在两个地方（装上时一个函数、卸载时另一个函数），清理成了没有强制的义务，作者忘一句就静默泄漏一份资源。VSCode 是现成的标本，它的问题是双重的。清理这半边：扩展的 deactivate 清理钩子只在宿主进程整体关闭时才运行，平时根本轮不到出场，制造影响和清理影响还被拆在两处，想核对清理是否干净都难。代价这半边：所有扩展跑在同一个宿主进程里，扩展的代码一旦执行过，宿主没有任何机制在运行中途单独摘掉它的影响，唯一的清理手段是重启整个宿主。所以安装量前 100 的扩展里，87 个含可执行代码（有代码执行过就有影响要清）的扩展，卸载时都得走重启这条路。

**论文怎么解：**规定每个改动在执行的当场交出两样东西：改完的状态，加一个撤销函数。谁改的谁交出后悔药，药方跟着动作走。运行时只保管一条越串越长的回执链（就是词典里的累加器），卸载组件时调用它一次，环境回到组件来之前的样子。而且「可撤销」被证明是可拼装的积木属性：两个可撤销的效果组合起来仍然可撤销，撤销顺序天然后进先出。

**类比：**装修留收据。工人每动一处，当场留一张「如何复原此处」的说明，房东退租时按相反顺序执行一遍。Ctrl+Z 的历史栈是同一个原理：后发生的先撤销。

**给你的启示：**让每个注册动作返回一个撤销函数。装工具、挂监听器、注册命令、写提示词片段，全部返回 undo。这一条借过去，热重载、卸载、权限回收就变成同一种操作：扔旧、装新。多份研读笔记都把它列为性价比最高的借用。

### 思想二：让依赖断供即歇业，而不是断供即报错

**问题是什么：**传统框架在启动时把线接好，之后不管。运行中依赖断了，用到它的代码要么抛错，要么拿到空值崩在更远处；想提前防，就得在每个组件里手写监控代码盯着上游。

**论文怎么解：**组件进门先交需求清单（规格）。环境每变一次，运行时拿新环境对照每份清单，把这次变化分成三类：从缺到齐，激活；从齐到缺，停用并自动恢复现场；其余，无关，不理会。这个分类一次都不会漏，因为论文规定所有环境变化都必须经过效应机制登记，而登记依赖这个动作本身就是可逆效应（它的撤销函数就是删掉这个键）。两套机制在这里咬合成一体。组件从此不写监控、不写判空：它要么在依赖齐全的语境里运行，要么根本没在运行。

**类比：**夜市摊位接隔壁摊的电源。隔壁收摊，你自动歇业；隔壁回来，你自动开张，不用雇人二十四小时盯着隔壁的电闸。餐馆门口挂牌「本店需要水、电、燃气」也是这个形状：市政停水那一刻，挂牌状态翻转，餐馆自动贴出暂停营业。

**给你的启示：**让插件声明依赖，缺了就安静待机，等依赖出现自动上线。换数据库后端时，只重启真正用到数据库的插件，其余原地不动。对 agent 项目这条尤其顺手：模型端点、记忆库、某个工具的凭据，全都可以做成声明式依赖。

### 思想三：所有交互走同一个门

**问题是什么：**两个坎。其一，「恢复原状」做不到逐字节：释放一块内存，堆的布局回不到分配之前；程序生成过一个名字，撤销只能是把它丢掉。其二，从正在运行的系统里摘掉组件时，它的撤销指令面对的是被别人改过的状态，凭什么还作数？

**论文怎么解：**把全系统的共享可变状态装进一个「语境」，立下纲领：组件和环境的每一次交互都经过它。做法是给每个键（带名字的储物格）配发一组合法操作，每个操作只许读写自己格子的地盘；组件被允许做的事只有两种，对键执行登记过的操作，或者安装新键。要是有人私接状态，比如某个分配器从语境外面的计数器抽号，按规矩这算不合规；补救办法是把它收编：把那个计数器也登记成一个键，它就合规了。全走一个门之后，两个坎都有了便宜的答案。互不干扰被拆成逐键的本地条件：不同格子的操作天然互不妨碍；同一格子内部的交换性，由格子的提供者在定义处一次性负责，所有使用方免检。「认证」具体是什么：在论文的形式模型里，它是钉在键定义上的一份数学证明；落到 Cordis 的真实代码里，它退化成一条设计义务，框架既不跑测试也不做运行时校验，靠提供者把操作写成天然可乱序的形状（注册表那种每条各占一条记录的形状天然合格，有序队列这种形状就得另想办法）。义务最终落在写这个键的人身上。「恢复原状」也放宽成「恢复到观察不出区别」，判定权交给键配发的操作集，没被任何键绑住的细节（堆布局、生成的名字）自动出局。

这里还藏着一个反直觉的设计杠杆：接口每多承诺一个细节，能安全乱序的操作就少一批。论文用系统接口举过一个例子，翻译过来是：两个发号窗口，A 窗口承诺「每次发最小的空号」，那么谁先来谁拿小号，先后一换、拿到手的号码就不同，次序就有了讲究；B 窗口只承诺「随便哪个空号都行」，先来后到就无所谓。发号规则（也就是接口承诺）直接决定哪些操作可以乱序、哪些必须排队。

**类比：**酒店前台的总账。住客想动任何东西都得记在总台账上，谁也不许私下配钥匙；正因如此，退房验收才能按「下一位客人察觉不出」的标准执行，不必逐根头发还原。

**给你的启示：**第一件事是说清楚你的项目里「共享状态的唯一入口在哪」，入口之外的状态不受任何保证保护。第二件事是审接口：返回值里没人用的承诺能砍就砍，砍掉一个承诺，就多一批可以安全乱序、独立撤销的操作。

### 思想四：装与卸是同一份合同的正反面

**问题是什么：**多数插件系统做成能装不能卸。就算能卸，「有人还在用我，我就不能走」的护栏看起来会死锁；边跑边改的系统还有一个更深的恐惧：改到最后，系统状态取决于中间经历了什么，改乱了就回不去。

**论文怎么解：**用三个对象和九条规则把整件事形式化。组件是岗位说明书（三份声明），fiber 是一次具体上岗（随身带一本后进先出的撤销清单，和一份「入职时谁在给我供货」的登记），注册表是花名册。九条规则里，人只能下三道命令（插入、退役、移除，都只下命令不亲手干活），剩下六条是系统自动流转的生命周期：激活三步（开工检查、干活并逐条记撤销、完工登记供货人），停用三步（贴停工告示停止供货、等依赖者走光再倒序清场、半途被叫停就转入撤出）。设计妙处有两个。其一，资源账直接从在岗名单推出来，系统不记第二本账，也就没有两本账对不上的问题。其二，停用护栏的自动放行：贴了停工告示的 fiber 立刻从资源账里消失，于是不会再有新依赖挂上来，老依赖发现供货人要走、顺次进入自己的停用流程，链条自动松开，死锁从结构上就不会发生。

在此之上论文给出四张字据：结构怎么折腾都不坏（保持性）；卸载精确到「像从没来过」（时间可组合性）；提供方先启动晚退场，施工途中供货人换人立即叫停重新适配（空间可组合性）；以及最实用的一条，终局只由最终配置决定，和中间装装卸卸多少个来回无关（进展与汇聚，两个词的意思见词典）。最后一条的意思是：只要全系统守着「共享状态都走语境」的纪律，你就可以放心边跑边做任何改装，因为结局和从头按最终配置装一遍完全相同；纪律之外的部分（发出去的数据、组件自己的内存）不在保护内，边界见第六节。第 4 章还立了两条配套纪律，后面借鉴清单会引用：一种资源只允许一家供应商申报，出问题永远找得到人；组件激活失败（端口被占、文件缺失）时，按自己的撤销清单拆干净、记录失败原因，不自动重试，也不连累邻居。

**类比：**拆迁先疏散租户，确认全走了，再动承重墙。停用一台数据库时，先宣布停机、停止对外供货、通知所有用它的插件，等它们全部安全拆完，自己才倒序撤销。

**给你的启示：**任何可插拔模块，装上它的时候就必须写清它怎么卸下自己，卸载要精确到「像没来过」。把卸载次序立成协议而不是默契。把「改配置等于退役加重插，终态等于按新配置从头装」立为系统性质，做到了这条，运行中改配置才真正敢做。

### 思想五：理论要能养出生态才算数

**问题是什么：**前四条都是纸面保证。一套编程范式，凭什么让几千个互不相识的作者愿意在它上面写代码？

**论文怎么解：**先看落地形状。Cordis 核心库只有五个动作：ctx.effect（干每件事附撤销说明书，是唯一改环境的入口）、ctx.set/get（登记与取用服务，登记本身带撤销，每次变动通知声明方重新评估）、ctx.isolate（同名依赖各拿各的）、ctx.intercept（叠使用规则，改规则不重启）、ctx.use（通电运转，开关由「依赖齐不齐」这个目标状态驱动；识别换人靠提供者的永不复用编号。为什么输出一模一样也要重新适配：系统记供货记的是人名而非货品，新旧数据库哪怕连接串完全相同，编号不同就是换了人，旧的那位马上要被拆走，下游必须重新接一遍。代价是偶尔多折腾一次重启，买的是绝不带着已经易主的依赖继续跑）。上面加一层声明式配置加载器和事务性热重载，到此为止。再看证据：Koishi 在这套核心库上跑了四五年，论文称有 4000 多个社区插件，插件作者互不相识，只靠声明的依赖名这一层契约协作；没有人手写卸载逻辑，但卸载永远干净，因为凡经 ctx 做的事自动登记、自动倒序收回。论文把这叫「本要靠每个作者自觉的正确性，现在由抽象一次性承担」。要把话说全：这套抽象消灭的是「忘写清理」，防不了「清理函数写错」。框架保证撤销函数一定会被调用，不保证调了真的还原（这一层的边界在第六节）。

**类比：**手动挡与自动挡。核心库是手动挡，加载器是自动挡：使用者只写愿望清单（配置树），加载器负责把现实改成和清单一致，改多少算多少，绝不推倒重来。

**给你的启示：**好抽象的标志是使用者少写代码。回头检查你自己的框架：插件作者还要手写清理吗？还要手写重连吗？这两处能被抽象接管，生态才养得大。判断成熟度时，Koishi 比 dsh 更有参考价值：前者用五年养出了大生态，后者七周 24 万 star 但自曝破坏性变更，热度与稳定是两回事。

## 四、仓库与论文的对应关系

四个点连成一条线，每个环节都验证过：

- **论文**：《A Programming Paradigm for Spatiotemporal Composability》（arXiv:2608.25512），北京大学与 DeepSeek-AI 合作，理论本体。
- **Cordis**：论文的实现，TypeScript 元框架（勘察时 8,938 star）。dsh 把它连同 loader、hmr、schemastery 等配套整体 vendor 进仓库，不靠外部版本漂移。
- **Koishi**：Cordis 养出大生态的先例。依赖链验证：koishi 包依赖 @koishijs/core 4.18.11，后者声明依赖 cordis ^3.18.1，也就是 v3 系。2026-10-01 本总览复核过这一条（初版沿用的「^4.6.0」是勘察笔记笔误，已订正）：jsdelivr 抓取 master 分支 package.json 原文，npm 注册表双向印证，cordis 与 @cordisjs/core 两个包的 3.x 最新版都是 3.18.1，v4 目前只发到 4.0.0 候选版（latest 为 4.0.0-rc.10），稳定版尚不存在。框架 2019 年 12 月创建，至今活跃。
- **dsh**：Cordis 在 AI Agent 领域的旗舰应用，口号「Everything is a Plugin」。TypeScript + MIT，2026-08-13 创建，勘察时 241,568 star，最近提交 2026-09-29（已发 0.2.0-rc.2）。packages/ 下 55 个包，apps/ 下 cli、web、desktop、desktop-host 四个入口，docs/ 下 60 余篇中英双语文档。

论文概念与 dsh 代码的对应表（左列出自论文正文，右列出自 dsh 的 architecture.md、cordis-primer、glossary；两列对上靠研读员解读，见第七节第 2 条）：

| 论文概念 | dsh / Cordis 对应物 | 一句话 |
|---|---|---|
| 统一语境 | `ctx` 对象与 `ctx.*` 稳定键（tools、llm、fs、sandbox、sessions 等） | 共享插线板，每个能力占一个孔 |
| 组件 | Plugin / Service | 插件就是组件的实现形态 |
| 可逆效应 | `ctx.effect()` 加 disposer；文档称「可回退注册」 | 装上去的每样东西都留撤销按钮 |
| 响应式反效应 | `inject` 依赖声明 | 写明我要什么，框架等就绪才启动 |
| 隔离 | `ctx.isolate`；dsh 的 per-agent scope（`agent.ctx`） | 同名依赖各拿各的 |
| 观察等价、换提供者 | 能力接缝三件套（接口+提供者+消费者），换 provider 整机生效 | 文件系统指到远程沙箱，shell、PTY、LSP 跟着搬 |
| 声明式配置与配置修订 | Profile、Bundle、Patch 三层组装（`cordis.patch.yml` 按 id 替换任意配置行） | 出厂配方，每层可被上层换掉，不 fork 即可改产品 |
| fiber | dsh 文档未出现此词，隔离角色由 scope 承担 | 见第七节第 1 条 |

dsh 还有三样论文没有直接展开、属于 agent 领域自己的设计，值得单独记：

1. **会话日志是唯一事实源**：模型看到的上下文完全从持久化日志投影，不变量是「模型可见即已记录」；JSONL 版本化存储，已提交的文件永不改名删除。调试、fork 会话、回放、换界面都从同一份日志出发。这和论文「配置树是唯一真相」是同一种思路在不同层的化身。
2. **瀑布式事件**：一批事件要求监听者调 next() 把工作交给下游，可以加工后再交，也可以短路拍板。拦截请求、改写工具调用都发生在挂监听器的地方。它与论文交换性纪律的关系存疑（第七节第 3 条）。
3. **turn 与 step 两个时间单位**：step 是一次模型请求加它引发的工具调用，turn 是从接纳一条输入到再无欠账的完整排空。

## 五、可借鉴思想清单

以下每条都有出处，思想一到五和第四节的展开就是它们的依据，括注标最近的对应位置；没有一条是撰写者的私货。

1. 给每个注册动作配一个撤销函数：装工具、挂监听器、注册命令的 API 都返回 undo，卸载、热重载、权限回收全走这一种操作（思想一）。
2. 把能力挂在公共上下文的稳定键名下（学 dsh 的 ctx.tools、ctx.llm），插件只认键名，不 import 具体实现（第四节对应表）。
3. 按「接口 + 提供者 + 消费者」三件套设计能力接缝，换文件系统实现时让 shell、终端这些依赖方整体跟随（第四节对应表）。
4. 让插件进门先声明依赖清单，依赖不齐就安静待机，等就绪自动激活，不报错也不轮询（思想二）。
5. 用永不复用的编号识别提供者：货可以一样，人不能认错；宁可偶尔多重启一次，也不让下游带着已经易主的依赖继续跑（思想五）。
6. 状态只记一本账：哪些能力可用，直接从「谁在岗」推出来，别再养一份可能对不上的资源名册（思想四）。
7. 把「改配置等于退役加重插，终态等于按新配置从头装一遍」立为运行时改动的目标性质，前提是共享状态都守着走语境的纪律（思想四、第六节）。
8. 热重载做成事务：先备份旧模块再换新，任何一步失败整体回滚，系统永不半新半旧（思想五）。
9. 学 dsh 把会话日志做成唯一事实源（模型可见即已记录，只追加、永不改名删除），界面、回放、调试都从它投影（第四节）。
10. 权限跟着声明走：插件只能读到它声明过的依赖，加载前就能审完整清单（论文第 6 章能力型安全，素材笔记 06）。
11. 审一遍接口承诺：没人依赖的返回值约定（比如「必须发最小的空号」这类）能砍就砍，换来操作可乱序、可独立撤销（思想三）。
12. 一个资源只允许一个提供者，第二家申报同名资源直接拒绝，出了问题永远找得到人（论文第 4 章配套纪律，思想四有述）。
13. 卸载次序立成协议：先停供、通知依赖者、等它们全部拆完，自己再按后进先出清理（思想四）。
14. 失败显式记录原因、不自动重试、不传染邻居组件（论文第 4.4 节对失败情形的处置，思想四有述）。
15. 给多租户或多 agent 场景加一层作用域隔离，同名依赖各拿各的，撤销时丢掉整层即可（思想三、dsh 的 scope）。

## 六、这套思想的边界与代价

先说最大的成本：纪律。「一切共享状态绑成键、一切交互走语境」是这套范式的前提，论文在第 31 页原话划界：绕过语境的共享位置落在定理保护之外。这意味着采用它是改造，一半状态走语境、一半不走的用法比不用更危险，因为你会误以为有保证。

其余的代价与边界：

- **撤销的正确性仍由作者负责。**框架保证到点执行撤销函数，但卡片上写的办法灵不灵，运行时不验证（第 59 页）。所以思想五说的「自动登记消灭的是忘写清理」，它防得了「忘了写」，防不了「写错了」。
- **内存状态不保留。**这套机制是「卸了重装」，组件自己的内存状态热重载后不保留，想留就得放进更长寿的依赖里。
- **边界外收不回。**数据一旦发出系统（写盘、发包）就只剩两条路：扣住不发，或者事后补偿（删文件、退款）；补偿的数学保证需要另行验证。
- **版本与命名是开放问题。**依赖按名字连接，接口漂移和键名撞车都会「连接成立但运行出错」，命名空间、peer 依赖、结构兼容三条路各有局限，论文自己承认没有统一解。
- **循环依赖查得出但拆着疼。**从声明就能静态检出，不会死锁（只会永久休眠），但拆起来要新写专门的胶水组件：论文举的例子，是互相需要的服务器和访问控制器，拆成两个互不依赖的内核，再加两个同时靠着两者的胶水件。组件一多胶水件涨得很快：十个互相缠绕的组件，最坏要新写几十个胶水件。正确性和运行速度不受影响，疼的是写配置和理解系统的人。
- **证据是观察性的。**单一生态、单一语言（TypeScript）、无对照实验、性能开销未量化。Koishi 生产环境跑的确实是 Cordis v3：论文脚注这么写，本总览 2026-10-01 复核的依赖声明（cordis ^3.18.1）也印证；论文讲的 v4 目前只发到 4.0.0 候选版，核心组合模型两个版本一致。

什么场景不值得用：一次性脚本、组件集合常年不动的工具，引入语境和生命周期管理是纯开销；性能极度敏感且高频触碰共享状态的路径（intercept 和 isolate 都有成本，具体多大没人数）；真正的不可信代码（能力检查挡不住绕过代理的恶意代码，仍需独立沙箱）；以及没有把握维持「都走语境」纪律的团队，纪律守不住，保证就是纸面的。

## 七、仍然说不清、存疑的问题

1. **fiber 在 dsh 里去哪了。**论文里 fiber 是核心概念，但 dsh 的 README、architecture.md、cordis-primer、glossary 全都没有这个词，dsh 用 per-agent scope 承担隔离子上下文的职责。是改名、封装进了运行时内部，还是有意不暴露，材料没说。
2. **概念映射表是解读，不是核对。**第四节那张表的左列来自论文正文，右列来自 dsh 文档，两边对上靠研读员的推断；packages/ 下 55 个包只勘察到目录名加架构文档的深度，源码未逐行读。
3. **有序拦截与交换性纪律的张力（本总览撰写者补充）。**论文明确点名「中间件的有序链不可交换」，说这类顺序敏感的东西得靠别的机制管；而 dsh 的核心拦截机制恰恰是瀑布式事件的 next() 有序链，监听者可以加工也可以短路。有序拦截和逐键可交换这两套秩序在 dsh 里如何分工共存，读到的材料没有明说。
4. **VSCode 的两个统计无法复现。**论文脚注给出两个数字：前 100 个扩展里，87 个含可执行代码、卸载时需要重启宿主进程；只有 7 个声明过对其他扩展的依赖。脚注自称检索于 2026-06-09 的 VSCode 市场，本机无法复现，只能照录。
5. **证明与形式细节全部跳过。**各定理只读了结论陈述，未复核证明。论文里有一处关于撤销函数的细节取舍，大意是：撤销函数按动手那一刻的状态定制，恢复时不必逐字节还原，只要恢复目标没被波及就算数；实现里怎么处理这一点，论文没给例子。另外笔记摘录的编号（定义号、定理号）转述自论文原文，可能有提取误差。
6. **语言无关性只有论述，没有第二实现。**换 Rust、Haskell、Python 的最小要求列了清单（闭包、模块动态装卸、类型扩展、访问拦截），但 Cordis 之外没有实现，实际移植工作量未知。
7. **性能没有数字。**论文承认抽象的性能开销未量化。dsh 仓库确有 benchmarks/ 目录，2026-10-01 查看了它的说明文件：套件按用户路径场景组织（会话开启、长会话浏览器、流式重连等目录），测墙钟时间与保留内存，说明文件本身不含任何阈值数字；也没有 intercept、isolate 的专项微基准。本次未运行任何基准，无法给出数字。
8. **数字都是时点值或转引。**dsh 241,568 star（2026-10-01 勘察）、Koishi 6,239 star、Cordis 8,938 star、Koishi 插件数（论文说 4000+，仓库勘察时官网口径 3000+），均未独立核实，会随时间变化。
9. **抓取与提取的方法限制。**github.com 网页版抓取超时，仓库信息以 GitHub API 与 raw 文件双路验证为准；论文 PDF 经 pdftotext/pypdf 提取纯文本，数学符号（花体字母、下标）可能有排版损失，笔记依据的是完整可读的英文叙述句；cordiverse 组织下的 cordis-primer 独立仓库 raw README 404，入门文档内容以 dsh 仓库内版本为准。
10. **dsh 的 API 会漂。**项目自曝 developer preview、会有破坏性变更，借鉴 ctx 键名、profile 体系这类 API 形态有随时过时的风险，思想比 API 稳。

## 八、答读者问（第一轮试读反馈）

**问 1：「提供者在定义处一次性认证交换性」具体是个什么动作？写数学证明、跑测试，还是运行时校验？这份义务最后落在什么工件上？**

论文层面和实现层面是两回事。在论文的形式模型里，认证是一份随键定义一起提交的数学证明，和「撤销必还原」的证明并列，是键定义的组成部分（论文第 29 页）。在 Cordis 的真实代码里，第五节笔记描述的五个原语（effect、set/get、isolate、intercept、use）中没有任何证明或校验设施，所以落地后它退化成一条设计义务：提供者把操作写成天然可乱序的形状（注册表式的一条记录一个坑），框架既不跑测试也不校验。落到你身上，这份义务的工件就是「你定义键的那段代码本身的形状」，没有单独的证明文件。需要说明：从「论文要求证明」到「实现里没有校验设施」这条连线是撰写者综合两份笔记的推断，论文没有专门一段讲实现里如何落实认证。

**问 2：Koishi 四五年实践里，插件作者把撤销函数写坏导致残留的真实频率有多高？**

回答不了。论文与七份笔记都没有失败率数据：论文给的是观察性证据（存在且有人用），没有统计清理缺陷发生率。可行的线索是 dsh 仓库 docs/ 下有 postmortem/ 子目录（勘察时见过目录名，未读），以及 Koishi 的 issue 跟踪，本次都没有翻。

**问 3：dsh 的瀑布式 next() 有序拦截，和论文「有序链不可交换」的纪律怎么分工共存？换拦截器那一刻靠什么保证不乱？**

说不清，已列在第七节第 3 条。能确认的只有两件事：论文把有序链划为需要别的机制管的形状；dsh 确实在用有序瀑布做拦截。两者如何在同一个系统里自洽、替换拦截器时靠什么保持秩序，读到的文档没有讲。Cordis 侧另有 ctx.intercept（读依赖前叠加规则、改规则不重启），它与事件瀑布如何配合，材料同样未覆盖。

**问 4：Koishi 到底在用 Cordis v3 还是 v4？**

v3，论文脚注和依赖声明两路一致。2026-10-01 复核：koishi master 分支的 packages/core/package.json 里，@koishijs/core 4.18.11 声明依赖 cordis ^3.18.1（v3 系）；npm 注册表上 cordis 的 latest 是 4.0.0-rc.10、@cordisjs/core 的 latest 是 3.18.1，即 v4 至今只有候选版和测试版，没有稳定版可迁。初版总览写的「cordis ^4.6.0」沿用了勘察笔记，经本次三路核查确认是笔记笔误（4.6.0 这个版本在两个包里都不存在），正文已订正。这也顺带回答了证据成色的问题：第五节「Koishi 先例」用的四五年数据发生在 v3 上，论文讲的是同一套核心模型的 v4。

**问 5：性能到底差多少？benchmarks/ 里有什么数字？**

没有数字可给。论文自己承认性能开销未量化。dsh 的 benchmarks/ 目录本次查看了说明文件：它按用户路径组织场景（会话开启、长会话浏览器、流式重连等），测墙钟时间与保留内存，说明文件只定义指标规范、不含阈值数值；目录清单里没有 intercept、isolate 的专项微基准；各包内部的 `.perf.ts` 诊断不在这个套件里。本次没有运行任何基准，所以 intercept 和 isolate 在 agent 高频工具调用路径上的实测代价，仍然是未知数。

**问 6：「永不复用编号，新旧输出一模一样也触发下游重新适配」，这样设计为什么是对的？不会无意义抖动吗？**

机制的理由：如果按「值一样就算没变」判断，系统会在提供者已经换人的情况下让下游继续用旧件，而旧件马上要被拆走，下游等于骑在一匹正在被牵走的马上。编号不同就是换了人，下游重新接一遍，保证读到的依赖永远来自当前在岗的提供者。你直觉里的「白白抖动」确实是这套设计的代价：货没变、只是换了个商家的场合，也会触发一次重启。论文的笔记里没有讨论这个取舍的天平，但机制本身（记人名不记货品、防「看起来一样其实来源变了」）出自论文第 4 章；「代价是偶发多余重启」这半句是撰写者按机制推出来的，论文没有明说。
