## 1. 仓库定位

一句话：这是 DeepSeek 开源的 **Agent Harness**（可以理解成「给 AI Agent 配的整机框架」：模型、工具、文件系统、审批、界面这些零件全装在一个可插拔的壳里）。

- 官方描述：**"DeepSeek Harness: Everything is a Plugin."**（一切皆插件）
- README 原文的关键句：产品的每个部分（模型适配器、工具注册表、会话日志、甚至 agent 循环本身）都是插件，都能通过配置替换；扩展方式就是在其他插件旁边挂载一个新插件，「没有特权核心需要打补丁」。
- 状态：**developer preview**（开发者预览版），README 用大写警告「THERE WILL BE COMPATIBILITY-BREAKING CHANGES」，还会破坏兼容。想借鉴要意识到这点。
- 运行方式：装好 Node.js 后 `npx @deepseek-ai/dsh web`，本地 3080 端口起一个 Web 界面。源码运行是 `pnpm install && pnpm run build && pnpm dsh web`。

## 3. 核心机制（读自 docs/architecture.md）

### 3.1 启动即组树：Profile / Bundle / Patch

dsh 启动时把自己组装成一棵插件树，组装规则像千层蛋糕，从下往上叠：

1. **Profile（配置档案）**：一串命名组合，内置模板有 `web`、`headless`、`sdk`、`sdk-minimal`、`acp`。`dsh web` 其实就是 `dsh --profile web`。
2. **Bundle（捆绑包）**：分发单位，在包的 `package.json` 里用 `dsh.bundle` 字段自我声明。`dsh-base` 是公共底层（模型适配器、工具、持久化、沙箱与审批策略、凭据、遥测），`dsh-web-app` 等再往上加浏览器界面或服务器。
3. **Patch（补丁）**：用户在自己的 `cordis.patch.yml` 里按 id 定位某一行配置整体替换，或插入新行。任何被打印出来的配置行都能被你的补丁顶掉。

大白话：产品出厂是一套配方，每一层都可以被上层换掉。你想改哪块，写个补丁声明「把 id 为 X 的那行换成我的插件」即可，不用 fork 整个产品。

### 3.2 服务挂在一个共享上下文上（ctx.*）

架构文档给每个核心包指定了一个稳定的 `ctx` 键，比如：`ctx.sessions`（会话日志）、`ctx.systemPrompt`（提示词组装）、`ctx.tools`（工具）、`ctx.agents`（agent 注册表）、`ctx.agentLoop`（默认循环）、`ctx.llm`（模型适配器）、`ctx.webhookRuntime`、`ctx.shell`、`ctx.fs`、`ctx.sandbox`、`ctx.jobs`、`ctx.commands`、`ctx.terminals`。

这像是公司前台的一块指示牌：找能力看牌子，谁挂牌子谁提供能力。其他插件只认牌子（`ctx.tools`），不 import 具体实现，所以实现可以随时被换掉。

### 3.3 事件分三个域

- **Session 事件**：持久事实，追加进日志并广播。要「重启后还在」的事实放这里。
- **Agent 事件（`agent/*`）**：携带活的 Agent 对象，用于观察或拦截进行中的工作。
- **能力事件（`fs/*`、`tools/*`、`telemetry/*`）**：给各类能力附加策略与适配器。

其中一批事件是「瀑布式」的：监听者拿到参数后必须调 `next()` 把工作交给下游，可以选择加工后再交，也可以短路（直接拍板不往下传）。一轮对话的骨架就是一串这样的瀑布：`turn/start` → `agent/pre-step` → `step/start` → `agent/request` → `llm/stream` → `tools/pre-execute → execute → post-execute` → `step/end` → `turn/end`。拦截请求、改写工具调用、拦截整个 turn，都在对应环节挂监听器。

两个时间单位：**step** = 一次模型请求加上它引发的工具调用；**turn** = 零或多个 step，从接纳一条输入到再无欠账为止。

### 3.4 会话日志是唯一事实源

模型看到的上下文完全从持久化的会话日志投影出来（`deriveMessages()`）。不变量是「模型可见即已记录」：运行时会检查模型请求能从日志完整重建。存储是 JSONL（可选 zstd 压缩），带版本号迁移机制，已提交的文件永不改名或删除。这设计对借鉴者很有价值：调试、fork 会话、回放、换界面，全都从同一份日志出发，不会有第二份真相。

### 3.5 能力接缝（capability seam）

术语表的定义：一个 seam 由三部分组成，**声明接口的 Service Definition + 实现它的 Service Provider + 使用它的 Consumer**。妙处在文档举的例子：文件系统和子进程共享同一个「执行世界」，把文件系统 provider 指向远程沙箱，Bash、PTY、LSP 全体跟着搬过去。换一个零件，整机换世界。这就是「一切皆插件」能兑现的原因。

## 4. 与论文的对应关系

### 4.1 论文本体

- 标题：*A Programming Paradigm for Spatiotemporal Composability*，arXiv:2608.25512（cs.PL），作者 Yifan Shi、Wei Zhang、Tianyi Cui（2026），配套仓库 https://github.com/cordiverse/paper ，状态「预印本修订中，以 arXiv 最新版为准」。
- 摘要思想（转述自 cordiverse/paper 的 README，论文全文本次未读）：
  - 现代软件（插件系统、自进化 agent 框架）需要动态组装零件，但缺形式化基础。论文拆出两个独立维度：**时间可组合性**（零件拆走时，它的副作用能被完整撤干净）和**空间可组合性**（零件之间的依赖是声明出来的，环境变化时自动决定谁该激活、谁该歇着）。
  - 解法是把编程语言理论里的 effect/coeffect 概念搬到运行时：**可回退效应**（每个上下文变化自带一个运行时逆操作，管时间维）+ **响应式协效应**（按组件声明的依赖分类环境变化，驱动激活与停用，管空间维）。
  - 两者统一成单一的「上下文类型」，形成所谓**上下文范式**；再合并出**组件**概念。落地实现就是 Cordis。

### 4.2 概念映射（论文 ↔ 代码）

| 论文概念 | 仓库里的对应物 | 通俗说法 |
|---|---|---|
| 上下文范式（context paradigm） | Context，`ctx` 对象 | 一块共享的插线板，每个能力占一个孔（`ctx.tools`、`ctx.llm`） |
| 组件（component） | Plugin / Service | 插件就是组件的实现形态：`apply(ctx)` 挂载，框架管生命周期 |
| 可回退效应（revertible effects）= 时间维 | `ctx.effect()` 注册 + disposer | 提示词片段、工具 schema、监听器装上去都留了「撤销按钮」，热重载或卸载时自动拆干净 |
| 响应式协效应（reactive coeffects）= 空间维 | `inject` 依赖声明 | 插件写明「我需要 ctx.llm」，框架等它就绪才启动我，启动顺序由依赖图决定 |
| 观测等价 / 组件可互换 | capability seam 换 provider | 接口不变，实现随便换，整机行为等价切换 |

需要说明：上表的左列来自论文摘要，右列来自 dsh 的 `docs/cordis-primer.md`（它列出五个概念：插件、上下文、inject 依赖注入、类型化事件、可回退注册）与 `docs/glossary.md`。逐条对应是我的解读，论文正文我没有逐章核对。

### 4.3 Cordis 与 Koishi

- **Cordis**（https://github.com/cordiverse/cordis ）：TypeScript，MIT，8,938 star，2022 年 5 月创建，2026 年 9 月仍有推送。自述「时空可组合性元框架」，API 尚不稳定。dsh 把它整体 vendor 进了仓库。
- **Koishi**（https://github.com/koishijs/koishi ）：跨平台聊天机器人框架，TypeScript，MIT，6,239 star，2019 年 12 月创建，2026 年 8 月仍在推送，官网 koishi.chat，生态号称 3000+ 插件，带控制台和插件市场。「Koishi 建立在 Cordis 上」这一点我做了依赖链验证：顶层 `koishi` 包 → 依赖 `@koishijs/core` 4.18.11 → 其 `package.json` 的 dependencies 里有 **`cordis: ^4.6.0`**（`GET /repos/koishijs/koishi/contents/packages/core/package.json`）。也就是说，Cordis 这套理论先在 Koishi 上跑了四五年、养出了三千个插件的生态，然后才被拿来做 agent 框架的地基。对借鉴者来说，Koishi 是「这套范式能不能养出大生态」的活证据。

### 4.4 关于「fiber」概念

任务提示论文概念含 context/component/fiber。**fiber 在本次读到的所有材料中均未出现**：dsh 的 README、architecture.md、cordis-primer、glossary 都没有这个词；论文摘要里也没有。dsh 文档里承担「按 agent 隔离子上下文」角色的是 **scope**（每个 agent 一个注册作用域，`agent.ctx`，可见性不向 subagent 继承）。它可能对应论文正文里的某个概念，但本次无法确认，如实存疑。

## 5. 它给使用者暴露了哪些概念

从「想拿来自定义一个功能」的使用者视角看，dsh 的概念面是：

- **配置面**：profile / bundle / patch（YAML），`dsh --profile web --dump-config` 能打印整棵启动树，打印出来的每一行都能被你替换。
- **插件面**：npm 包形式发布，打上 `dsh-plugin` 主题就能被社区发现；插件实现某个 Service，用 `inject` 声明依赖。
- **扩展点面**：加模型走 `ctx.llm`，加工具走 `ctx.tools`（schema 自动进提示词组装），拦请求/工具/turn 走对应 `agent/*` 或 `tools/*` 事件，改文件系统走 `ctx.fs` 或 `fs/*` 事件，限进程走 `ctx.sandbox`，还有 `ctx.jobs`、`ctx.commands`（人发的斜杠命令，不进模型）、`ctx.goals`（会话级持久目标）、实验性的 `ctx.agentTeams`（多 agent 协作：花名册、任务板、邮箱）。
- **作用域面**：全局注册与 per-agent scope 两层，同名时「最具体者胜出」（shadowing）。
- **SDK 面**：TypeScript SDK 与 Python SDK；SDK 自动选 `sdk` profile；另有 ACP 服务器入口。
- **界面面**：Web UI、Electron 桌面版、headless 一次性运行器，全部只是不同 profile 下的插件组合。

## 7. 对想借鉴者的三句话

1. **最值得偷的思想**是把「撤销」做成一等公民：插件装上去的每样东西（工具、提示词片段、事件监听器）都返回一个撤销函数，热重载、卸载、权限回收全都变成同一种操作。这是论文「时间可组合性」的工程兑现，自己的插件系统加这一条，脏状态问题能少一大半。
2. **第二值得偷**的是「能力 = 接口 + 提供者 + 消费者」三件套：接口稳定，实现可换，换一次全局生效（文件系统指到沙箱，shell 跟着搬）。依赖只看牌子不看成品的规矩（`ctx.tools`）是它的前提。
3. **先想清楚再抄**：项目自曝「会有破坏性变更」，且 star 热度高不等于 API 稳定。Koishi 用五年时间证明这套范式养得起大生态，这比 dsh 七周 24 万星更有参考价值。
