# 研读笔记：第 70–83 页（第 6–8 章）边界、启示与相关工作

## 一、这部分解决什么问题

论文前半部分给出了机制：每个副作用都登记一份"怎么撤销"，每个组件声明"我需要什么"。第 6 章回答工程师接手后一定会问的问题：这套机制的适用范围在哪，哪些它做不到，遇到现实工程问题（负载均衡、滚动更新、权限、循环依赖、版本漂移）怎么落地。第 7 章把它和已有方案逐一对表，说清各自的取舍。第 8 章收束全文，并给出作者最看重的应用方向：自进化的 AI Agent 运行环境（论文称 agent harness，可以理解为"给 AI agent 用的工具箱和操作系统"）。

## 二、核心概念逐个讲

### 1. 系统边界：什么能撤销、什么不能
判据很朴素：一个位置，只要系统独占地能改它、且能把它恢复到改动前，它就在"界内"，操作可撤销；两条缺任何一条就在"界外"，操作不登记也不撤销。边界按"位置"画而不按"介质"画：同一块内存，只有本系统写就是界内，别的进程也在写就是界外；同一个文件系统，私有目录下的草稿文件是界内，别的程序也会动的路径是界外。把边界往外推是有代价的：环境得为每个访问提供"可撤销"的语义。

往外走的操作分两段。获取阶段（打开文件、申请内存、启动子进程）在界内登记一条记录，可撤销；发射阶段（写数据、发网络包）把数据送出了边界，收不回来。对发射只有两种补救：一是扣住不发，等产生它的状态确定能持久了再发；二是补偿，用一个粗略还原的动作顶上，比如删掉刚建的文件、退掉刚收的钱。补偿同样按"后进后出"的顺序叠加，但论文的数学保证是针对严格撤销证明的，换成补偿就要重新验证。

### 2. 服务多路复用：一个中介带来负载均衡和滚动更新
一份服务可以有多个提供者。直接的做法是独占绑定，同一时刻只挂一个，切换时所有使用者都被短暂打扰。更妙的是服务中介（broker，可以想成前台总机）：提供者和使用者双方都接入这个中间人，请求由它分发。关键在于提供者的注册本身是可撤销效果，卸载即自动从路由表消失。于是三件传统上属于运维的事变成了应用内部的普通机制：负载均衡（按轮询、最少负载或延迟加权分发请求，加机器减机器就是装卸组件）；滚动更新（新提供者先加载注册，激活后流量渐渐切过去，旧的等在途请求清空再卸载，论文说这把容器编排层面的操作降维成了应用层的组合模式）；跨进程调用（每个进程有自己的 context，远程访问靠 RPC 穿针引线；既然跨进程会慢、会中途失败，这类接口必须按异步契约设计）。

### 3. 能力型访问控制与沙箱
权限问题分两层。第一层是约束组件能访问什么：组件只能读到它声明过的依赖，声明相当于"申请钥匙"，context 相当于"发钥匙的柜台"。因为申请清单在代码里静态写明，加载前就能审完，这就是能力型安全的思路：权限跟着手里的引用走，而不是跟着"你在哪个环境里"走。拦截机制还能带细粒度策略，比如给文件系统依赖标注哪些路径可读写，给社区插件只读数据库、给核心组件全量权限；拦截挂在 context 上，双方代码都不用改，运行中随时可调，也不触发重载。第二层是不可信代码：恶意组件能绕过代理直接摸底层对象，语言级检查就失效了，必须靠真正的执行边界（独立运行时、沙箱进程、虚拟化容器）。不可信组件通过一座"桥"拿宿主的依赖，用起来和本地注入没有区别，而桥本身在宿主侧就是一根普通组件，权限可以削减。

### 4. 语言无关性：换一门语言需要什么
时间维度（能装能卸）最起码要闭包，撤销动作得能存成值、卸载时回放；此外模块要能动态装卸。托管运行时（Node.js）有可编程的模块注册表，原生代码用 dlopen/dlclose 这类动态链接接口，WebAssembly 看宿主是谁。空间维度（能声明依赖）归结为依赖注入问题，分两层：类型层面要能扩展 context 类型，Haskell 的 typeclass、Rust 的 trait、TypeScript 的模块增强都能做到；运行层面要能透明拦截属性的读取，JavaScript 的 Proxy、Python 的描述符协议就是干这个的，没有这类原语就退而用运行时反射，代价是类型安全和开发体验。Rust 过程宏、Zig comptime 这类编译期元编程可以两层一起给。

### 5. 循环依赖
A 要 B、B 要 A 时，两个组件不会死锁，只会永远休眠。这和并发系统的死锁不同：死锁取决于运行时的调度，要边跑边抓；循环依赖从声明本身就能算出来，加载时就能报告。实践中多数循环可以拆开：论文举例，服务器和访问控制器互相需要，拆成两个内核加两个集成件后，两个内核互不依赖，只有集成件同时依赖两者。这种拆法原则上总能做，但 n 个互相互动的组件最坏要拆出平方级数量的集成件；不影响正确性和性能，伤的是开发体验（配置、命名、理解成本）。缓解靠打包、按约定自动接线、脚手架生成样板这些工程手段。

### 6. 依赖版本与接口漂移
模型里依赖靠"名字相同"建立连接，这在独立开发的生态里有两个漏洞。接口漂移：提供者改了接口，消费者还按老接口声明，连接照样成立，运行时却会报错或悄悄走样。键名撞车：两家无关的提供者用了同一个名字，消费者拿到的完全是别的东西，比漂移更难诊断。三条应对路：给键名加包命名空间，撞车从构造上消除，但把包注册表耦合进了模型；用包管理器的 peer 依赖做版本约束，安装期就能查出不兼容，这是 Cordis 现在的做法，局限是依赖各家自觉遵守语义化版本，且一个包只能装一个版本；按结构比对接口是否兼容，记录类型好办，行为契约难，某些情况下不可判定。三条如何统一，论文承认是开放问题。

### 7. 和语言、操作系统的协同设计
语言侧能做两件事：把 context 变回隐式，省去处处传参，也堵住"误摸到别的组件的 context"这种漏洞；让编译器认识效果和依赖，循环依赖就能在编译期报出，依赖也能按类型结构而不是名字比对。操作系统侧的图景更大：今天的操作系统只在进程粒度上提供"可装卸"，容器编排只在服务粒度上提供"可组合"；协同设计的系统可以让组件声明的依赖就是它全部够得着的东西（WebAssembly 模块实例化时只拿到宿主给的导入，就是这个模型），操作系统发放资源时顺手记账（内存、文件描述符），事务写盘和写时复制存储还能把"只能扣住或补偿"的操作变成真正可撤销。

## 三、相关工作：它和谁比、差别在哪

撤销一侧（第 7.3 节）分四族。DSU、Erlang/OTP、JS 热更新这类"状态前移"方案搬内存状态更优雅，但要手写迁移函数，而且 Cordis 能整个卸载并回收资源，代价是组件自己的内存状态重载后不保留（除非放进更长寿的依赖里）。OSGi、VSCode 插件、Command 模式、事件溯源都靠开发者手写清理，撤销是没强制的义务，忘了就静默泄漏。React 的 useEffect 在结构上最接近（effect 返回清理函数），败在不可组合：只能写在组件顶层，不能进条件循环，不支持异步，所以效果拼不出复合的撤销；Cordis 只要求给每个原子效果配一个撤销，复合效果的反向操作自动推导。软件事务内存、RAII、可逆计算能在固定范围内自动回滚，但范围要预先圈定，Cordis 的撤销跟随组件整个生命周期，两者互补。系统层的 Nooks、shadow drivers 由平台记账回收，是最接近的先例，但平台只能回收它认识的东西，Cordis 的组件能自定义效果。

接线一侧（第 7.4 节）分三族。Spring、Vue 的 provide/inject、React Context 在启动时接线，提供者换掉时在用的组件既不失效也不重建。OSGi 的声明式服务和 iPOJO 会随服务出现消失而启停，最接近本文，但停用靠手写回调且是同步的，异步清理没有协议可等；Cordis 用自动回滚加"惯性卸载"状态（清理跑完才响应下一个变化）补上这两个洞。FRP 和 signals 在"值"的粒度传播变化且有防毛刺保证，Cordis 在"组件"粒度、没有"一轮"的概念，两者互补。

范式层面：COP 的"context"指执行情境，切换的是跑什么行为，不管效果回收；Cordis 管的是装了什么效果、依赖是否满足。AOP 的切面隐形织入全局，代码自己不知道被织了；Cordis 的对应物是显式声明的依赖，影响面就是声明的那张清单，编排者不读源码就能在配置层审查。

## 四、结论与 AI Agent 的关系

第 8 章把全文收成一句话：可撤销效果管"装得上也卸得干净"，响应式依赖管"缺了就休眠、来了就唤醒"，统一的 context 让不同组件的效果互相独立；实现是 Cordis 框架，用 Koishi 这套生产系统（4000 多个社区插件）做了验证。作者最看重的下一步验证场景是自进化 agent harness：AI agent 持续生成并替换自己的运行环境组件，几乎不需要人盯。快速替换考验"拆得干净"，拓扑频繁变动考验"接得稳"，这套范式的两个保证正好一一对应。参考文献里引了 OpenAI 的 harness engineering 和 Anthropic 的 harness 设计文章，说明这条线索来自真实工程实践，对做 agent 项目的读者是直接的信号。

## 五、面向非程序员最重要的三个要点

1. 能撤销是设计出来的。多数系统的清理靠开发者自觉写，忘一句就漏一份资源；这套系统把 undo 做成每个动作的必配项，撤销顺序自动叠加。但边界外收不回：数据一旦发出（写盘、发包），只剩"先扣住再发"和"事后补偿"两条路。借鉴时先想清楚自己系统的边界画在哪。
2. 依赖是活的。传统框架启动时接好线就不管了；这里缺件的零件自动休眠、来件自动唤醒，只有真正受影响的零件重启，负载均衡和滚动更新只是这套机制的自然推论。任何做"工具箱可插拔"的项目都能受益。
3. 对自进化 Agent，这是论文眼里最有价值的验证场。一个 AI 持续改写自己工具箱的系统，最怕垃圾越堆越多、依赖越改越乱；"每个动作登记可撤销的逆操作"和"依赖不满足就休眠"两条底线，值得做 agent harness 的开源项目直接借鉴。
