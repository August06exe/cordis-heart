# 这套思想，什么时候别用

## 最大的成本，叫纪律

这套范式有一笔进场费。它的所有保证都建立在一个前提上：**一切共享状态绑成键，一切交互走语境。**

语境像一栋楼唯一的大门，保安只在这个门执勤；从窗户翻进来的状态，出了事没人赔。把它接进现有系统，动的是结构：共享状态要一件一件绑回键上。最危险的用法是走一半：一半进语境、一半留在外面，你会误以为整套系统都在保护之下，而真正没人管的，恰好是留下来的那一半。

## 六条边界，逐条说清

**01 撤销的正确性仍由你负责**——框架像闹钟，到点一定响；响过之后动作对不对，闹钟管不着。它防「忘了写清理」，防不了「写错了清理」。

**02 内存状态不保留**——字面动作是卸了重装。想留住状态，就把它搬进比组件更长寿的依赖里。

**03 边界外收不回**，数据一旦发出系统（写盘、发包），撤销函数就够不着了，只剩扣住不发，或事后补偿。

**04 版本与命名是开放问题**——依赖按名字连接，接口一漂、键名一撞，就是「连接成立但运行出错」：名字对上了，人对错了。

**05 循环依赖查得出但拆着疼**，能静态检出，不会死锁，只会永久休眠。拆开要新写胶水组件，十个缠在一起的组件，最坏要新写几十个。

**06 证据是观察性的**，只有一种生态、一种语言的实践，没有对照实验；Koishi 生产环境跑的还是上一代版本，论文讲的是下一代。

## 五个场景，先问纪律，再问开销

| 场景 | 是否适用 |
| --- | --- |
| 一次性脚本、组件集合常年不动的工具 | **不适用**：纯开销 |
| 性能极度敏感且高频触碰共享状态的路径 | **不适用**：intercept 和 isolate 的成本还没有数字 |
| 真正的不可信代码 | **不适用**：能力检查拦不住绕过代理的恶意代码 |
| 团队没把握长期坚持「一切交互都走同一个入口」的纪律 | **不适用**：坚持不住，保证就停在纸面上 |
| 自进化 agent harness（快速替换组件、拓扑频繁变动） | **适用**：快速替换接住「拆得干净」，频繁变动接住「接得稳」 |

## 可带走物 · 采用前自查五问

```
共享状态能全部绑成语境键吗？有一条绕行（全局单例、模块级缓存），这条就不过。
组件真的需要运行中动态装卸吗？集合常年不动，开销一分都收不回来。
热路径会不会高频触碰共享状态？拿到实测数字之前，别把「应该不大」当结论。
要跑的代码里有不可信的吗？这套范式不替代独立沙箱。
团队真能长期坚持这条纪律吗？所有交互都走同一个入口，一条都不能漏——半途而废，比不用更危险。
```
