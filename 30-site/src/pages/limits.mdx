## 最大的成本，叫纪律

这套思想的所有保证，都建在一个前提上：**一切共享状态登记进语境，一切交互走同一扇门**。

这意味着采用它不是加一个库，而是一次改造：你的共享状态要一件件搬进门里。最危险的是只搬一半。一半进门、一半留在外面，你会以为整个系统都在保护之下，而真正没人管的，恰好是留在外面的那一半。

## 六条边界

**撤销对不对，靠作者。** 框架保证回执到点一定执行，但回执本身写错了，框架发现不了 <R id="obligation" />。它防得了「忘了写」，防不了「写错了」。

**组件自己的内存不保留。** 卸载就是撕回执，热重载就是拆旧装新。组件内存里攒的东西想留住，得放进一个比它活得更久的依赖里。

**发出去的，收不回。** 系统能独占、能还原的地方叫界内，界线就是<T id="boundary" />；写到磁盘的文件、发出去的网络包在界外，那里的操作不记账，也不撤销 <R id="boundary" />。出了界只剩两条路：扣住先不发，或者事后补偿，比如删掉文件、退还扣款 <R id="compensate" />。

**名字对上了，人可能不对。** 依赖只按名字连接。组件各自开发、各自发版时，提供方改了接口，使用方还按老样子用，名字照样对得上，跑起来才出错 <R id="drift" />。论文承认这还没有统一的解法。

**循环依赖查得出，拆着疼。** 两个组件互相需要，结果是两个都永远待命；好在光看依赖声明就能发现，加载时就能报出来 <R id="cycle" />。拆开的办法是把它们切细，再写专门的「胶水」组件分别连两边。正确性和速度不受影响，疼的是写配置、读系统的人。

**证据是观察性的。** 只有一个生态、一种语言，没有对照实验，开销没有量化 <R id="threats" />。dsh 还在 developer preview，接口随时会变。

## 哪些场景适合，哪些不适合

| 场景 | 判断 |
| --- | --- |
| 一次性脚本、组件常年不动的小工具 | 不适合：没有要撤的东西，纯开销 |
| 性能极度敏感、高频读写共享状态的热路径 | 慎用：额外开销还没有数字 |
| 要运行不可信的代码 | 不够：仍需独立沙箱 |
| 插件生态，作者互不认识 | 适合：Koishi 就是这个场景 |
| 会频繁给自己换零件的 agent | 很适合：论文点名的下一个验证场 <R id="agent" /> |
